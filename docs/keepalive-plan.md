# 校园网「保活 + 断线自动重连」方案设计

> 状态：**已实现**（2026-11-11）
> 最终选择：以「心跳保活」为核心 + 静默 HTTP 重登兜底（可一键关闭）+ 托盘/通知/部署全做
> 实现位置：`jitauth/keepalive.py`（引擎）、`jitauth/tray.py`（托盘）、
> `jitauth/__main__.py`（`--watch` / `--status` / `--verify-http-login`）、
> `install_task.ps1`（`JIT-Campus-KeepAlive` 任务）、`tests/test_keepalive.py`（测试）

---

## 0. 先给结论

**推荐：方案 2「常驻看门狗」，并在里面内置方案 1 的轻量心跳。**

- 开机那一次登录保持现状（`JIT-Campus-AutoLogin`，登录后 45 秒跑一次，几秒就结束）
- 再挂一个常驻进程（登录后 120 秒启动）：每 60 秒探一次网，在线就什么都不做；掉线就**静默 HTTP 重登**（不开窗口），必要时才升级到浏览器
- 心跳让它"不容易掉"，看门狗让它"掉了马上回来"——两者互补，缺一个都会漏

如果你不想有常驻进程，退而求其次是方案 3（计划任务每分钟跑一次 `--quick`），效果接近，但粒度粗、日志更吵。

## 1. 现状诊断

### 1.1 现在的运行模型

| 环节 | 现状 |
| --- | --- |
| 触发 | `install_task.ps1` 注册的计划任务，**只在用户登录时**触发一次（+45 秒） |
| 主流程 | `jitauth/__main__.py` → 连 WiFi → 探针判断 → 看门户 → 未登录则浏览器登录 → `return`，进程退出 |
| 运行期 | **没有任何巡检**。进程退出后，网络状态再没人管 |
| 任务限制 | `ExecutionTimeLimit = 10 分钟`、`MultipleInstances = IgnoreNew`、`RestartCount = 2` |

也就是说：它能覆盖"开机那一刻没登录"，但完全覆盖不了"登录之后又掉了"。

### 1.2 日志里的证据

`logs/autologin.log` 最近的记录显示，几乎每次开机都要重新登录一次：

```
2026-10-21 07:40:31 [INFO] 浏览器登录成功：页面出现成功/已在线提示
2026-10-23 12:38:55 [INFO] 浏览器登录成功：页面出现成功/已在线提示
...
2026-11-09 21:15:16 [INFO] 浏览器登录成功：页面出现成功/已在线提示
2026-11-10 13:53:54 [INFO] 网络已连通，无需再次认证
2026-11-11 07:58:01 [INFO] 网络已连通，无需再次认证
```

- 10-07 到 11-09 之间，**每次开机都是"未登录"状态**，需要重新认证
- 11-10 / 11-11 两次因为关机时间短、会话还没过期，开机时直接就是在线的

结论：网关侧的会话本来就**活不过一次关机**，运行期间的空闲超时大概率同理。所以"开机登录一次"这个模型注定只能解决一半问题。

### 1.3 现有代码里可以直接复用的能力

好消息是核心零件都齐了，不需要重写：

| 能力 | 位置 | 备注 |
| --- | --- | --- |
| 外网探针（generate_204） | `portal.internet_ok()` | 已能识别 204 / 200 / 被门户劫持 |
| 纯 HTTP 静默登录 | `portal.login_via_http()` | **不开窗口**，自适应表单（DDDDD/upass 已实测可识别） |
| 门户在线/离线判定 | `portal.drcom_online_state()` / `portal.judge()` | 已修过"注销页假成功"的坑 |
| 浏览器登录 | `browser.login_via_browser()` | CDP 直连，可复用已开窗口 |
| WiFi 检测/重连 | `wifi.ensure_connected()` | 含开无线电、等 SSID |
| 日志 | `logging_setup.get_logger()` | 需加轮转 |

**唯一的不确定项**：`login_via_http()` 在本校真实门户上还有没有效。日志里 9-27 成功过一次（`HTTP 登录成功：门户返回成功提示：认证成功`），但之后浏览器路径一直先成功，HTTP 路径就再没被真正触发过。这一点需要在 P0 阶段实测（见第 5 节）。

## 2. 掉线原因 → 方案覆盖矩阵

先把"为什么掉"拆开，否则方案会选错：

| # | 原因 | 典型表现 | 心跳能防 | 重登能救 | 备注 |
| --- | --- | --- | --- | --- | --- |
| 1 | 网关空闲超时（N 分钟无流量） | 挂机不动时掉，一动就掉 | ✅ | ✅ | **你说的"开屏放着"最可能是这个** |
| 2 | 会话时长上限（如 12/24h 强制下线） | 每天固定时间掉一次 | ❌ | ✅ | 心跳无效，只能重登 |
| 3 | DHCP 租约到期换 IP | 掉线后门户里 IP 变了 | ❌ | ✅ | Dr.COM 绑 IP+MAC，必须重登 |
| 4 | 睡眠 / 休眠 / 现代待机 | 合盖再开就断 | ❌ | ✅ | 需要"唤醒即检" |
| 5 | WiFi 断连 / 漫游 / 信号弱 | 换位置、走出范围 | ❌ | ✅（含 WiFi 重连） | |
| 6 | 手机等设备抢登（单终端限制） | 两边互相踢 | ❌ | ⚠️ 会互踢 | 需要"不抢"策略，见 4.5 |
| 7 | 门户维护 / 策略变更 | 门户本身打不开 | ❌ | ❌ | 只能告警，别疯狂重试 |

**关键判断**：原因 1 是"预防"，原因 2~6 是"恢复"。只做心跳解决不了 2~6，只做重登又会让 1 频繁触发重登（多一次无谓的闪断）。所以最优解是两者都要，且心跳为主、重登为兜底。

## 3. 候选方案

### 方案 1｜纯心跳保活（只防闲置）

**做法**：每 3~5 分钟发一次极小的外网请求（HEAD / 204 探针），让 NAT / AC 的会话保持活跃。

- 改动量：小（约 100 行）
- 覆盖：只覆盖原因 1
- 风险：几乎为零，不碰账号密码
- 缺点：会话到期、换 IP、睡眠唤醒一律救不了；本质是"降低掉线概率"，不是"保证在线"

### 方案 2｜常驻看门狗（探测 + 静默重登 + 心跳）★ 推荐

**做法**：登录后拉起一个长期驻留的 Python 进程（`pythonw -m jitauth --watch`），循环执行：

```
每 60s:
  1. 探测连通性（2~3 个独立探针，任一通即在线）
  2. 在线 → 每 4 分钟发一次心跳；每日志一条摘要；睡觉
  3. 连续 3 次失败 → 看门户页，确认是"未登录"而不是"门户故障"
  4. 未登录 → 静默 HTTP 重登 → 复查探针
  5. HTTP 失败 → （可选）无头浏览器 / 可见窗口重登
  6. 仍失败 → 指数退避，限流，等下一轮
```

- 覆盖：原因 1~5 全覆盖，6 有专门策略
- 优点：**恢复时间 60~90 秒**；全程静默无窗口；策略集中，好调
- 缺点：多一个常驻进程（Python 约 20~30 MB）；需要处理崩溃自启

### 方案 3｜计划任务高频巡检（无守护进程）

**做法**：给主程序加一个 `--quick` 模式（只探针 + 必要时 HTTP 重登，跳过 WiFi 长等待和浏览器），计划任务每 1~2 分钟跑一次，跑完就退。靠 `MultipleInstances=IgnoreNew` 防重入。

- 覆盖：与方案 2 基本相同
- 优点：**无常驻进程**，进程崩了下一分钟自然重来；实现量最小；任务计划里看得见
- 缺点：最小粒度 1 分钟；每分钟一次 Python 冷启动（约 0.5~1 秒）；日志按次刷；做不了"30 秒内恢复"和精细退避

> 补充：现有程序其实**只要加个 `--quick` 再挂个重复触发器**就能跑通 70%，是性价比最高的"最小改动版"。代价是日志会变吵（每分钟一个启动块），且掉线时如果 HTTP 不通会按现有逻辑弹浏览器窗口——必须先把弹窗行为收住。

### 方案 4｜页面内 JS 自愈（不推荐）

保留浏览器窗口，页面里注入 `setInterval` 定时检查并重新提交。

- 优点：几乎零额外进程
- 缺点：窗口必须永远开着；浏览器一崩/一关就失效；页面跳转后脚本丢失；和"想安静挂机"的诉求冲突
- 结论：只能当玩具，不做主方案

### 方案 5｜协议级心跳（不推荐）

抓包分析 Dr.COM 客户端与 AC 之间的保活报文，定时重放。

- 优点：最贴近官方行为，可能根本不会掉
- 缺点：要抓包 + 逆向，协议可能加密，学校改版就失效；维护成本极高；有合规风险
- 结论：投入产出比太差，不做

### 横向对比

| 维度 | 方案 1 心跳 | 方案 2 看门狗 ★ | 方案 3 定时巡检 | 方案 4 页面 JS | 方案 5 协议 |
| --- | --- | --- | --- | --- | --- |
| 防空闲掉线 | ✅ | ✅ | ✅（1 分钟粒度） | ⚠️ | ✅ |
| 会话到期能恢复 | ❌ | ✅ | ✅ | ⚠️ | ❌ |
| 唤醒后能恢复 | ❌ | ✅（唤醒即检） | ✅（下次触发） | ❌ | ❌ |
| 恢复速度 | — | 60~90 秒 | 60~180 秒 | 不确定 | — |
| 是否弹窗 | 不会 | 默认不会 | **需先改** | 窗口常在 | 不会 |
| 常驻进程 | 要 | 要 | **不要** | 不要 | 要 |
| 改动量 | 小 | 中 | **最小** | 小 | 极大 |
| 抗崩溃 | — | 需重启策略 | **天然** | 差 | — |
| 锁号/互踢风险 | 无 | 可控 | 可控 | 中 | 低 |

## 4. 方案 2 详细设计（推荐方案）

### 4.1 进程与生命周期

- 新模块 `jitauth/watch.py`，入口 `python -m jitauth --watch`
- **单实例**：用 Windows 命名互斥体（`ctypes` + `CreateMutexW("Global\\JITAUTH-Watch")`），第二个实例直接退出 0
- 与一次性任务共存：一次性任务 45 秒跑完就退；看门狗 120 秒启动，第一轮探针通常已在线，直接进入待机
- 收到 Ctrl+C / SIGTERM / 注销时干净退出（写一条"看门狗退出"日志）

### 4.2 状态机

```
              ┌──────────── 每 check_interval 探一次 ────────────┐
              ▼                                                  │
          [ONLINE] ──连续 fail_threshold 次失败──▶ [SUSPECT]     │
              ▲                                     │            │
              │                          门户确认＝未登录          │
              │                                     ▼            │
              │                                [RECOVERING] ─────┘
              │                                     │ 失败
              │                                     ▼
              └──────── 探针恢复 ────────────── [DEGRADED]（退避、只记录）
                                                    │
                                   账号错误 ──▶ [PAUSED]（停手，等人）
```

- **ONLINE**：一切正常，只发心跳，日志每 30 分钟一条摘要
- **SUSPECT**：失败不足阈值，先不下结论（防止一次抖动就重登）
- **RECOVERING**：确认未登录，执行重登阶梯
- **DEGRADED**：门户打不开 / 重登反复失败 → 指数退避，不刷日志
- **PAUSED**：门户明确说密码错误 / 欠费 → 立即停手，避免锁号

### 4.3 探测（怎么判断"断了"才准）

单个探针不可靠（某个域名被墙、DNS 抽风都会误判），所以：

1. **多探针**：默认 3 个，任一通即算在线
   - `http://connect.rom.miui.com/generate_204`（现有）
   - `http://www.msftconnecttest.com/connecttest.txt`（内容含 `Microsoft Connect Test`）
   - `http://captive.apple.com/hotspot-detect.html`（内容含 `Success`）
2. **连续失败阈值**：`fail_threshold = 3`，间隔 60 秒 → 最快 3 分钟才判定断线
3. **门户二次确认**：判定断线后先 `GET http://10.50.0.10/`，
   - 返回"注销页" → 其实在线，只是探针被拦 → 记 WARNING，**不重登**
   - 返回登录页 → 确实离线 → 重登
   - 门户都打不开 → `DEGRADED`，先修 WiFi / 等，不刷登录
4. **唤醒检测**：同时记录 `time.monotonic()` 和 `time.time()`；若某次 sleep 的墙钟间隔远超预期（>2.5×）或墙钟跳变 > 90 秒，判定"刚从睡眠醒来"，**立即探测一次**，不等下一个周期

### 4.4 恢复阶梯

```
第 1 级：HTTP 静默重登         portal.login_via_http()      ~1~2 秒，零窗口
第 2 级：无头浏览器重登        Edge --headless=new + CDP    ~3~5 秒，零窗口（可选，默认关）
第 3 级：可见窗口重登          browser.login_via_browser()  有窗口（可选，默认关）
```

- 默认只启用第 1 级；第 2、3 级用配置开关打开
- 每一级之后都**用探针复查**，通过才算成功
- 浏览器重登默认 `close_after_login = true`（用完即关），避免挂机时堆窗口

### 4.5 防抖 / 防锁号 / 防互踢（这块最关键）

| 风险 | 对策 |
| --- | --- |
| 频繁重登触发门户风控或锁号 | `max_relogins_per_hour = 12`；连续失败指数退避 `30s → 2min → 5min → 15min`（封顶） |
| 密码错误还一直试 | 命中 `FATAL_WORDS`（密码错误/欠费/用户名不存在）→ 立刻 `PAUSED`，只写日志，等你处理 |
| 手机和电脑互踢（单终端限制） | 统计"登录成功后 N 分钟内又掉"的次数；连续 3 次 → 判定为被抢占，退避 30 分钟并 WARNING，不参与拉锯 |
| 误判导致无谓闪断 | 三重门：多探针 + 连续失败阈值 + 门户确认，缺一不重登 |
| 两个实例同时登录 | 命名互斥体 + `MultipleInstances=IgnoreNew` |
| 门户维护期疯狂重试 | 门户不可达连续 5 次 → `DEGRADED`，15 分钟后再试 |

### 4.6 日志与可观测

- **只在状态变化时写 INFO**：`在线 → 疑似断线 → 正在重登 → 已恢复（耗时 42 秒）`
- 探针失败、心跳细节写 DEBUG
- 每 30 分钟一条摘要：`[摘要] 已在线 3 小时 12 分，今日重登 1 次`
- 日志加**按天轮转**（现在是单文件一直追加，常驻后会越来越大）
- 新增 `--watch-status`：打印看门狗是否在跑、运行时长、最近一次重登时间、今日重登次数（不依赖进程通信，直接读状态文件 `logs/watchdog.state.json`）

### 4.7 配置草案（向后兼容，新增 `keepalive` 段）

```jsonc
"keepalive": {
  "enabled": true,
  "check_interval": 60,        // 巡检间隔（秒）
  "heartbeat_interval": 240,   // 主动心跳间隔（秒），0 = 关闭心跳
  "probe_timeout": 4,
  "fail_threshold": 3,         // 连续失败几次判定断线
  "confirm_portal": true,      // 判定断线前先看门户页
  "on_sleep_wake": true,       // 唤醒后立即探测
  "relogin": {
    "engine": "http",          // http（默认） / browser / auto
    "max_per_hour": 12,
    "backoff_seconds": [30, 120, 300, 900],
    "verify_timeout": 25,
    "browser_when_http_fails": false,   // 是否允许升级到浏览器
    "browser_mode": "headless"          // headless / visible
  },
  "wifi_reconnect": true,      // 断线时先修 WiFi
  "log_summary_minutes": 30
}
```

### 4.8 部署改造（`install_task.ps1`）

新增开关 `-Watchdog`（或默认一并安装），注册第二个任务：

| 设置 | 值 | 理由 |
| --- | --- | --- |
| 任务名 | `JIT-Campus-KeepAlive` | 和现有任务分开，互不影响 |
| 触发器 | AtLogOn + 120 秒 | 排在首次登录任务之后 |
| 动作 | `pythonw.exe -m jitauth --watch` | 无窗口 |
| ExecutionTimeLimit | **无限制（0）** | 常驻，现有 10 分钟限制必须改 |
| MultipleInstances | IgnoreNew | 防重复 |
| RestartCount / Interval | 999 / 1 分钟 | 崩了自动起 |
| 电源 | 允许电池启动、不因切电池停止 | 笔记本必须 |
| `-Remove` | 同时删两个任务 | 避免残留 |

可选第二道保险：一个每 15 分钟跑一次的"守护任务"，只检查看门狗在不在，不在就拉起来（成本几百毫秒）。如果你觉得多余可以不做。

### 4.9 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| HTTP 登录在本校已失效 | 只能退回浏览器，会弹窗 | P0 先实测；失效则默认启用无头浏览器 |
| 无头浏览器被门户识别/拦截 | 重登失败 | 配置可切可见窗口；日志明确提示 |
| 重登会把旧会话踢掉 | 若误判，网络闪断几十秒 | 三重门确认后才重登 |
| 常驻进程被杀 | 失去保护 | 任务计划重启 + 可选守护任务 |
| 常驻占内存 | 20~30 MB | 可接受；CPU 几乎为 0（每 60 秒一次 HTTP） |
| 校园网限制多设备 | 和手机互踢 | 抢占检测 + 退避，不硬抢 |

## 5. 分期实施（每期都能单独验收）

| 阶段 | 内容 | 产出 | 验收 |
| --- | --- | --- | --- |
| **P0** | 实测 HTTP 登录是否有效 | 一份实测结论 + 必要时调整 `login_via_http` | 手动在门户注销后，`python -m jitauth --http-only --force` 能登回去 |
| **P1** | `watch.py` 骨架：探测 + 状态机 + 单实例 + 日志 + 唤醒检测 | 只探测、不重登，可安全挂机观察 | 挂 2 小时，日志能准确记录在线/断线，不误报 |
| **P2** | 接入 HTTP 重登 + 复查 + 退避限流 | 掉线能自愈 | 手动注销后 ≤90 秒自动恢复；连续制造 5 次掉线不触发限流异常 |
| **P3** | 计划任务部署（`-Watchdog` / `-Remove` / `-Status`） | 开机自动常驻 | 重启电脑 → 2 分钟内看门狗在跑；注销重登后仍在跑 |
| **P4（可选）** | 无头浏览器兜底、托盘图标、系统通知 | 增强 | — |

另外会给 `tests/` 补一个 `test_keepalive.py`（mock 探针与门户，不切网不开窗），保持现有"离线自测"的习惯。

## 6. 最终选择（已确认）

1. **方案**：心跳为核心（巡检本身就是每 60 秒一次流量），静默 HTTP 重登作为兜底。
   想退回严格纯心跳：`keepalive.relogin.enabled = false`。
2. **重登方式**：只走纯 HTTP，全程不开窗口；不弹浏览器、不做无头浏览器升级。
3. **范围**：引擎 + 托盘 + 气泡通知 + 计划任务部署，全做。

> 说明：方案 1（纯心跳）本身不含重登，而"只走 HTTP 静默重登"和"全做含托盘"都要求有重登能力，
> 因此落地时把重登做成**可关闭的开关**（默认开）——功能只多不少，随时能退回纯心跳。
